# Native service security evidence

The existing DashboardAccess boundary records actual .NET private authentication failures and authorization denials after the decision. Identity, Analytics and Notification services use their existing DashboardStore connection to the application's primary database. DeviceService observes actual JWT API 401/403 decisions when `DASHBOARD_DATABASE_CONNECTION` is configured; absence does not create a new required dependency. No second identity store or broker subscription is added. Node remains the owner of its own authentication/role/configuration/ingestion decisions and deterministic findings.

`SecurityObservation` emits a strict owned `ot-security-evidence/v1` envelope with source namespace `smart-factory-dotnet`, an immutable UUID, actual UTC occurrence time, explicit mode, fixed service identity, denied outcome/reason and no request/user/credential payload. Caller fields cannot choose authority. `SECURITY_NATIVE_MODE` defaults to `live` for actual deployed service decisions; isolated tests set `simulated` plus `SECURITY_SCENARIO_RUN_ID` (or replay plus `SECURITY_REPLAY_RUN_ID`). Never silently reclassify a queued event.

Records enter the existing primary `security_outbox` under producer `dotnet-services` with their complete original envelope. The application migration creates the outbox and the application's Node runtime handles source policy, stable deduplication, quarantine/retry, immutable evidence and versioned findings. Security capture uses the existing managed pool (maximum two connections per DashboardStore), a two-second linked timeout, 1.5-second statement bound and shared advisory capture lock. Capacity is 10,000 unacknowledged events; acknowledged delivery rows may be pruned to make room. Capture failures emit a bounded once-per-minute warning without SQL/request/secret details and never change the real access decision. The workspace's source/outbox/capture diagnostics must be reviewed before field commissioning; logging is not a promise of lossless capture through database outages.

`SECURITY_ENABLED=false` disables capture. The module has no Onesa/LLM/SIEM/feed dependency and no automatic control/PLC/firewall/credential/firmware action. It does not fetch public certificates from caller URLs or infer attestation from a self-reported hash. Optional Pi sampling is owned by the separate gateway checkout and remains a manual opt-in.

Run the normal .NET test project; `SecurityObservationTests` checks actual rejected-status classification, UTC/mode/run validation, fixed service identity and absence of invented attributes. The combined deployment acceptance suite additionally submits an actual anonymous IdentityService request and waits for its durable outbox to reach the Node cybersecurity workspace. The existing service/telemetry/AAS/notification tests remain required.

The current serving topology is the combined ARM64 API plus **one** telemetry/notification worker on Oracle, and a separate Vercel UI. Follow the frontend checkout's `deploy/oracle/README.md`, not the legacy Render release path. Build with the tested backend context, validate the six-service bundle and image audit, preserve existing environment files and MQTT client ID, stop the old worker before starting a replacement, deploy/wait for API first and then start the singleton worker. The cybersecurity migration is additive; rollback retains tables/evidence and selects the prior image. Do not deploy collectors or firmware to physical hardware automatically.

The frontend checkout owns complete workflow, rule, permission, retention, strict import/export and threat-boundary documentation in `docs/cybersecurity.md` and `docs/cybersecurity-api.md`. These are ordinary application release inputs, not a shared peer-platform schema/package. Independent local implementation and hosted deployment do not certify IEC 62443/NIS2 or establish external consumer/hardware acceptance.
